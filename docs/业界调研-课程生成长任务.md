# 业界调研：AI 课程生成如何处理长任务

> 调研时间 2026-11-17。对象是 GitHub 上仍在活跃的 AI 教育项目，重点看**生成流程的工程结构**，不看 UI 和选题。

## 二、OpenMAIC 怎么做（重点）

它**没有**用「一个 agent 跑完整门课」，而是把生成拆成**代码控制的步骤机**，模型只是每一步里的一个函数。

### 1. 步骤表：比「一课」还细

`lib/server/generation/run/plan.ts`：

```text
material-analysis → research → outline → [等用户确认大纲] → agents
→ 每个 scene 依次：content → actions → narration
```

实际 step id 是 `scene:{index}:{content|actions|narration}` —— **一页幻灯片拆三步**。我们的一课大概等于他们十几个 step。

### 2. 检查点：每步一行

`lib/persistence/generation-runs.ts` 里三张表：

```sql
generation_runs        -- 一行一个 run：state / step / scenes_completed / lease_*
generation_run_steps   -- 已完成步骤的产物，(run_id, step_id) 主键
generation_run_events  -- 有序事件日志，seq 递增，供 SSE 回放
generation_run_commands-- 按 command_id 幂等，重复命令返回首次结果
```

`state` 取值：

```text
preparing | outlining | awaiting_outline_confirmation
| generating | paused | completed | ended
```

注意 **`awaiting_outline_confirmation`**：大纲生成完就停下来等人确认，再开始写正文。这是把「白跑一整门课」的风险前置到最便宜的一步。

### 3. 崩溃恢复：租约 + 心跳 + 接管

`lib/server/agent-runtime/config.ts`：

| 参数 | 默认 | 含义 |
|---|---|---|
| `scanIntervalMs` | 1000 | 扫描待执行任务 |
| `heartbeatIntervalMs` | 2000 | 运行中刷心跳 |
| `leaseTtlMs` | 10000 | 心跳过期判定为孤儿，可被其他实例接管 |
| `maxConcurrent` | 2 | 单实例并发会话 |
| `maxAttempts` | 5 | 连续无人值守重启上限 |

写操作带 `lease_generation` 栅栏：租约被接管后，老 worker 的写入直接失败，不会双写。

**恢复 = 从最后一条 `generation_run_steps` 继续**，不是从头再来，也不需要用户点任何东西。

### 4. 重试与超时：按步骤类型分别定

`run/retry.ts`：首场景最多重试 2 次，后续场景 5 次；TTS 的 400 类拒绝不重试。
`run/deadline.ts`：

| 步骤 | 预算 |
|---|---|
| 场景正文 | 300s / 次 |
| 场景交互 | 60s / 次 |
| 每段旁白合成 | 30s |

失败被分类成「可重试 / 不可重试」，而不是一律退避。

### 5. 前端断线重连 = 事件重放

事件有 `seq`，前端带 `lastSeq` 重连，服务端从该序号续推。我们目前是 200 条环形缓冲，语义弱一档。

### 6. 密钥在服务端

`openmaic.yml` 里配置 provider，key 在 `.env.local`。**这是他们能做到「关掉标签页继续跑、进程重启自动接管」的前提。**

### 7. 两类生成并存

- **一键生成**：上面这套确定性步骤机，模型每步一次调用，prompt 由代码拼装。
- **Workbench agent**：带 24 个 skill 的对话式编辑，工具化改页面。用于「生成之后的迭代」，不是用于首次生成。

### 8. 上下文天然紧凑

`steps/scene-content.ts` 里，每一步都是「大纲条目 + 该场景素材」拼一个新 prompt，**历史不参与**。长任务不靠压缩历史，靠把任务切到小到不需要历史。

## 三、其他项目的做法

- **classbuild**：五阶段（Setup → Syllabus → Research → Build → Export），逐章生成、逐章流式渲染，key 只在浏览器。关页面即停，所以另配了 `scripts/generate-course.ts` CLI 做批量兜底。
- **coursetitan**：Moodle 插件，BYOK，单请求 300s 上限，README 专门写了「进度只在最后出现 = 你的 web server 在缓冲输出」。
- **CourseForge**：Python `threading` 起后台线程跑生成，进程重启任务即丢，没有检查点。
- **anything-to-course**：不给运行时，只给一份课程设计 Skill（先用后讲、间隔复习、隐藏答案）。说明这个领域很多人把方法论和工程分开卖。

## 四、对照我们的方案

| 维度 | OpenMAIC | 我们（当前） | 判断 |
|---|---|---|---|
| 生成单元 | scene × 3 步 | 一课一 run | 方向一致，粒度更粗 |
| 谁控制循环 | 代码 | 模型（agent 自主决定下一步） | 他们更抗「模型自己停下」 |
| 检查点 | 每步落库 | `lessons/*.md` 落盘 | 等价 |
| 崩溃恢复 | 租约接管，无人值守 | 标 `paused`，等人重连 | 弱，但受 BYOK 约束 |
| 失败策略 | 分类重试 + 分步超时 | 一律退避 5/15/45s | 他们更精细 |
| 进度回放 | seq 事件日志 | 200 条缓冲 | 我们弱 |
| 人工检查点 | 大纲确认 | 无 | **值得抄** |
| 上下文 | 每步独立 prompt | 线性累积 | **必须补** |
| 子 agent | 不用 | 讨论过 | 不是业界做法 |

## 五、结论

1. **「一段 run 写完一门课」业界没有**，我们的判断是对的。
2. **业界连“一课”都不给模型自主决定**，而是代码派活、模型干活。模型负责写内容，不负责决定「接下来干什么」。
3. **没人用子 agent 做课程生成**。子 agent 解决的是上下文隔离，而他们靠「每步独立 prompt」天然隔离，不需要多一层。
4. **他们能全自动恢复，代价是密钥在服务端**。我们选了浏览器 BYOK，就必须接受「重启后人工参与」。这是产品取舍，不是工程缺陷。
5. 我们有两点比他们弱且容易补：**失败分类**、**事件 seq 回放**。
6. 有一点可以直接抄：**大纲先确认再写正文**，把白跑成本压到最低。

## 六、据此对我们的改动建议

按性价比排序：

| 优先级 | 改动 | 理由 |
|---|---|---|
| P0 | 每课前重置窗口 + prompt 带完整课程计划 | 补上下文，等价于他们的「每步独立 prompt」 |
| P0 | 失败分类：400/401/403/内容拒绝不重试，直接 paused | 现在 429 和 key 错误一样退避 3 次，浪费 65 秒和 token |
| P1 | 单步超时按类型（正文 300s、画布 60s） | 现在只有全局 300s |
| P1 | 事件 `seq` + 重连回放，替代 200 条缓冲 | 断线恢复语义正确 |
| P2 | 大纲确认（`create_course` 后暂停，等人确认） | 最便宜的人工检查点 |
| P2 | 课程页显示 step 级进度 | 对齐他们的 `scenes_completed / scenes_total` |
